## なぜこのリストがあるか

出典：[素人とプロの差は、「手を抜く」場所に出る。｜すてぃお](https://note.com/suthio/n/n61e945d82363)

要旨：素人の雑さは均一で、プロの雑さには濃淡がある。判断基準は「あとでどうとでもなるか」の1点。運用開始後に直すコストが跳ね上がる場所（アーキテクチャ・データ構造・セキュリティ・認証）は最初から丁寧に、あとで直せる場所（見た目・文言・コードの綺麗さ）は堂々と雑に作る。

重要：「あとでどうとでもなる」状態を作ること自体に投資する。バランス数値は外部データ化さえできていれば無限にやり直せる側に移る。

## 取り返しのつかない項目（ゲーム開発版）

### 1. アーキテクチャ：シミュレーションと描画・入力の分離
ゲームロジックを「入力 → 純粋な状態遷移関数 → 新しい状態」の形にし、エンジンAPI（Update/deltaTime/Animatorイベント）に依存させない。描画は状態を読むだけ。後からこの分離を入れるのは全面書き直しになる。

### 2. データ構造：セーブ・リプレイ・キャラ/技データの外部化
- 数値・パラメータはコードにベタ書きしない（ScriptableObject / JSON）
- セーブデータ・リプレイには必ず version フィールドを入れる（1バイトの有無で旧データの生死が決まる）
- 運用開始後のマイグレーションは誰が作っていても高コストのまま

### 3. 決定性（ゲーム固有の追加項目）
同じ入力列から必ず同じ結果が出ること。リプレイ・ロールバックネットコード・バグ再現の前提条件。シミュレーション系でも乱数シード管理として効く（バグ再現・検証の再現性）。

### 4. チート耐性（セキュリティの翻訳）
原則は「クライアントを信用しない」。ローカル専用なら堂々と N/A。

### 5. 認証
オンライン要素（アカウント・レート・フレンド・課金）を一つでも入れるなら最初から。自前実装はしない（既製品を使う）。オフライン専用なら完全に N/A。

**クロスプラットフォーム配信との関係（全企画共通・2026-07-19）**
- 複数プラットフォームに出すだけ → 認証不要。セーブは各プラットフォーム標準で足りる
- クロスセーブ → 自前アカウント基盤が必要。ここで初めて認証が必須になる
- クロスプレイ → 認証＋サーバ必須
- セーブはプラットフォーム非依存のフォーマット（JSON等）＋version 管理が前提。先にやっておけばクロスセーブは「あとでどうとでもなる」側に移る

## 訂正：モックは捨てない（2026-08-01・全企画共通）

★ **モックをベースに Unity で作り直す。移行できるものはそのまま使う。**
- HTML/JS モックは捨てるための試作ではなく、Unity 実装の素材
- データ構造・設計判断・文言は持っていける形なら持っていく
- 捨てるのは表示層と JS 固有の仕組みだけ

→ **不可逆判定はモック段階から適用する。**
- データ構造の設計は、Unity に持っていける形かで判断する
- ロジックに埋め込んだ値や分岐は、移行時に書き直しになる
- JSON で表現できるものはデータに出す方が、移行時に得
- ただし「何でもデータに出す」ではない。**条件式を JSON に持ち込むと JSON がコードになる**ので、そこは線を引く

# 判定：地獄極楽六道縁途（エンド）（2026-10-01・モック着手前）

> **以下の〇×はすべて見込み**（まだ何も確かめていない）。モック着手前に、判定フローに沿って付けたもの

## 判定フローへの答え
- 対戦・競技要素：なし（1人用）
- オンライン対戦・協力：なし
- アカウント・ランキング・課金：なし
- 長期セーブが核か：**中**。一日ごとに進み、前日の判決が翌朝のニュース・翌日の再審・数日後のニュースに効く
- 数値調整を繰り返すか：**はい**（質問の一日の持ち分30回、線香の3分、強制判決の10秒・1分、残業代など）
- 乱数：**あり**（強制判決のランダム送り、エンマの博打）

## 項目ごとの判定（見込み）

| 項目 | 判定 | 理由 |
|---|---|---|
| シミュ/描画分離 | 〇 | 判定のロジック（線香の時間計測、質問回数、評価からニュースを選ぶ処理）を画面から切り離す。企画側で決定済み |
| データ構造（外部化/version） | ◎ | この企画の中身は「一件の台本」のデータそのもの。形式がそのまま移行コストになる。下の「不可逆の芯」参照 |
| 決定性 | 〇 | 競技ではないが、乱数（ランダム送り・博打）はシード固定。バグ再現と、決め打ちの翌朝ニュースの再現に使う |
| チート耐性 | N/A | 1人用で、ランキング・投稿を入れる予定がない |
| 認証 | △ | 全企画共通の判断。クロスセーブをやるなら要。セーブは JSON＋version にしておけば後から間に合う |

## 不可逆の芯（モック段階から丁寧に作るところ）
1. **一件の台本の形式**：計器（五戒の5欄）／上流の報告／エンマの観察／弁明／証人（伝え方の型＋内容）／質問8問への答え／真相／行き先ごとの評価（妥当・冤罪・見逃し）／ニュース（評価ごとの既定＋行き先ごとの上書き）。**version を入れる**。一件ずつ安定した ID を持たせる
2. **判決の記録**：どの亡者を、いつ、どこへ送ったか（強制判決・ランダム送りかどうかも）。翌朝のニュース、翌日の再審、数日後のニュースがすべてここを読む。2026-09-25 の時点で「判決記録の形式が不可逆寄り」と懸念済み
3. **幕間（アドベンチャーパート）のデータ**：いつ・どの条件で出すか、を台本と同じく外に出す
4. **数値の外部化**：30回・3分・10秒・1分・残業代・処理件数あたりの稼ぎ

## 堂々と手を抜くところ
絵（エンマの表情、罪人の背中、火の玉の動きは仮の図形）、効果音、画面のレイアウトの細部、ニュースや台詞の文言（データに出してあれば後で直せる）

## 線を引くところ（遠征の裁定を引き継ぐ）
条件式を JSON に持ち込まない。「この評価ならこのニュース」の選択規則はコード側、文面はデータ側
